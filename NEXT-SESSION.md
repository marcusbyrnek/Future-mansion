## Rebuild the film from scratch (no internet except pypi/github needed)

```bash
python3 -m venv .venv && .venv/bin/pip install pillow imageio-ffmpeg
.venv/bin/python build/make_cards.py     # makes build/cards/*.png
.venv/bin/python build/build_video.py    # ≈ 15–20 min on a typical box
```

`build/build_video.py` now **reuses existing clips** (skip-if-exists), so after a
first run, editing one scene only re-renders that scene + the final xfade pass.

## Environment traps (learned the hard way)

1. **Sandbox resets wipe untracked files** (anything git-ignored, e.g. `out/`).
   The MP4 must be re-downloaded by the user the same session it's produced.
2. **npm registry TLS is broken** (`UNABLE_TO_VERIFY_LEAF_SIGNATURE` even with
   `--strict-ssl=false`). Do NOT use npm. Use `pip install imageio-ffmpeg`
   (static ffmpeg binary) via venv. pip works fine.
3. **Image generation cap ≈ 10 images per turn.** Budget accordingly; generate
   in parallel batches of ≤10.
4. **GitHub Release uploads are impossible from the sandbox** — `github.com`
   and `api.github.com` work, but `uploads.github.com` is unreachable. If the
   user needs the file, either (a) they download via a local HTTP server / Arena
   viewer the same session, or (b) user creates the Release themselves and
   drag-drops it.
5. **A permanent repo copy of the MP4 is intentionally not kept** — it's a 132 MB
   media file and `out/` is git-ignored. Keep it that way.
6. Web VS Code cannot execute anything (no terminal runtime) — pasting build
   commands there does nothing. Only real terminals work (local PC, or this
   sandbox/Arena environment).
7. `pkill -f <pattern>` can kill your own shell if the pattern appears in your
   own command line. Use `ps aux | grep [x]pattern` first.
